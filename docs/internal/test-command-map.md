# Test Command Map

| Command | Purpose | Requires Secrets |
| --- | --- | --- |
| `npm test` | Run the Node test suite (`test:js`). `pretest:js` first builds the Angular dist chain. It is the one `@openreceive/*` import under `tests/` that has no tsconfig `paths` entry. | No |
| `npm run check` | Run the fast local gate: `validate` (JSON/schema/vector/provider validation plus generated-doc-table freshness), then `scan:secrets`, then `scan:naming`. | No |
| `npm run test:ci` | Run the full repository gate: `test:ci:core` then `test:ci:release`. | No |
| `npm run test:ci:core` | Deterministic source gate. It is exactly what `ci.yml` runs on each push: `check`, lint, format check, workflow check, generated-model freshness, public-API surface check, typecheck, Vue and Svelte checks, dead-export check, JS tests, package smoke. | No |
| `npm run test:ci:release` | Release-shaped gate. It builds packages, then runs Ruby, Python, PHP, .NET and artifact lanes in parallel, four at a time by default (`OPENRECEIVE_CI_JOBS` overrides). The artifact lane runs, in order: demo container and release checks, the Rails currency-drift check, demo builds, the client-bundle scan and the docs build. Check standalone parity after Python refreshes its vendored copy. Each lane prints its own log and duration. Any lane failure fails the gate. | No |
| `npm run test:live` | Live NWC smoke test against a real wallet (Node + Ruby). It is never part of the deterministic gate. | Yes |
| `npm run test:e2e` | Playwright end-to-end suite. It boots the node-express Buy a Button demo in `DEMO_WALLET=testkit` mode and drives real Chromium through all four framework tabs (lightning, swap + refund, remint, persistence). Run `npm run build:packages` first. The demo's vite server resolves `@openreceive/*` to the built dists, and a stale dist fails the boot with a missing-export error. CI builds before every run for the same reason. Server stdout is piped through (demo boot / `on_paid`, OpenReceive INFO). Set `LOG_LEVEL=DEBUG` for more OpenReceive detail. Pass `--headed` / `--ui` to watch the browser. The full suite runs weekly in `demos.yml`. | No |
| `npm run test:e2e:smoke` | Only the lightning spec's React tab, against node-express. This is the per-push `e2e-smoke` job in `ci.yml`. | No |
| `npm run test:e2e:smoke:fastify` | The same smoke spec against the fastify demo (`OPENRECEIVE_E2E_STACK=fastify`). It is the second step of the `e2e-smoke` job. | No |
| `npm run test:e2e:smoke:fastapi` | The same smoke spec against the FastAPI demo (`OPENRECEIVE_E2E_STACK=fastapi`). Its Vite config spawns `uv run uvicorn` and proxies the API paths, so the harness command stays the same. Needs `uv`. It is the third step of the `e2e-smoke` job. | No |
| `npm run test:e2e:smoke:php-plain` | The same smoke spec against the plain-PHP demo (`OPENRECEIVE_E2E_STACK=php-plain`). Its Vite config copies the standalone checkout build into `public/openreceive/`, spawns `php -S` and proxies the API paths, so the harness command stays the same. Needs PHP 8.2+ with `ext-gmp`, and Composer. `composer install` runs on first use. This is the weekly `buttons-php-plain` job in `demos.yml`. | No |
| `examples/buttons/server/php-plain/bin/ci` | The plain-PHP example's CI. It is the twin of the Rails `bin/ci`, for a host with no test framework. It runs `composer validate`, `php -l` on every file, the catalog/artwork drift check, and the shared-boundary check (no `shared/server-node` or React imports). Then it boots the stack in testkit mode and drives it with curl: order → invoice → cross-site 403 → `/__testkit/settle` → `payments/check` → the paid order and its download. | No |
| `npm run release:composer:plan` / `release:composer:build` | `plan` is a read-only Composer release plan. It checks `Version.php` and the Laravel `~X.Y.Z` constraint against the root version, lists the split repositories, and shows whether each package is committed. `build` creates one `git subtree split` branch per package under `release/composer/<pkg>/<version>`. It fixes up the Laravel `composer.json` by stripping the path repository, and verifies that the root `composer.json` has no `path` repository. `--snapshot` builds from the working tree. `publish-composer.yml` publishes (`packagist` environment). `release:composer:publish` is the fallback for a maintainer's machine. | No |
| `npm run test:orms` | Real-ORM adapter lane. knex, typeorm, and prisma each drive the payments repository through their `@openreceive/http` factory on sqlite. It generates the Prisma client first. The per-push unit tests check the factories against fakes. This lane proves them against the actual ORMs. It is the weekly `orm-adapters` job in `demos.yml`. | No |
| `npm run check:public-api` | Diff every publishable package's export surface against the committed snapshot (`tools/validate/public-api.snapshot.json`). This gate protects the curated adapter and wrapper surfaces. After reviewing a change, regenerate the snapshot with `--update`. | No |
| `npm run check:vue` | Type-check the Vue wrapper with `vue-tsc`. | No |
| `npm run check:svelte` | Type-check the Svelte wrapper with `svelte-check`. | No |
| `npm run validate` | Contract/vector validation plus generated doc-table freshness (spec route/error tables, headless symbol inventory), the kernel-table cross-checks (OpenAPI and JSON Schema enums against `spec/data/kernel-tables.json`), and vector coverage per engine (`spec/test-vectors/coverage.json`). Vector validation runs here. There is no separate `test:vectors` command. | No |
| `npm run scan:secrets` | Scan public repo files for likely committed receive-only NWC codes and reject tracked env files. | No |
| `npm run scan:naming` | Fail on the two-word spelling of the product name in any tracked file. The name is `OpenReceive`, one word, everywhere. | No |
| `npm run scan:client-bundles` | Scan generated demo `dist` bundles for browser-side NWC markers after `build:demo`. | No |
| `npm run check:standalone` | Verify the standalone checkout build (`packages/js/elements/dist/standalone/`), which is the last step of `build:packages`. It checks that the build is one self-contained ESM file with no imports or `require()`, that it registers `<openreceive-checkout>`, that the `MANIFEST.json` hashes and version match the tree and `package.json`, and that the `scan:client-bundles` secret markers find nothing. | No |
| `npm run generate:models` | Regenerate the contract constants, kernel tables and the FixedFloat decision table from OpenAPI, AsyncAPI, `spec/data/kernel-tables.json` and `spec/data/swap-state-table.json`. Output goes into TypeScript (`core`, `http`, `node`), Ruby (`openreceive/generated/tables.rb`), C# (`packages/dotnet/.../Generated/OpenReceiveTables.cs`), PHP (`packages/php/openreceive/src/Generated/`) and Python (`packages/python/openreceive/src/openreceive/_generated/`). | No |
| `npm run typecheck` | Typecheck all JS/TS packages and the Buy a Button server/demo TypeScript. | No |
| `npm run test:js` | Run the Node test suite, including browser/react/elements/framework adapter contract tests and real Vue/Svelte/Angular wrapper mounts. | No |
| `npm run test:ruby` | Run the Ruby tests against shared vectors and receive-only behavior. Tests are found by glob in each gem. Each gem's own `rake test` also works from its directory. | No |
| `npm run test:python` | Tests the Python engine (`packages/python/openreceive`) through `tools/ci/python-tests.sh`. It runs `uv sync --frozen`, then pytest over every `tests/**/test_*.py`, then `tools/conformance/python-crosslang.py`. The pytest run covers: vector conformance for every family the `python` coverage entry does not exclude, the HTTP golden files, the SQLAlchemy repository on SQLite (plus Postgres/MySQL when `OPENRECEIVE_TEST_PGSQL_URL` / `OPENRECEIVE_TEST_MYSQL_URL` are set), the testkit fixtures, the app over the fakes, the FastAPI router through `TestClient`, the CLI verbs, and the NWC transport against an in-process relay. An empty test glob is a hard failure. Needs `uv`. CI (`python-engine`) runs it on 3.10 and 3.13 with Postgres and MySQL service containers, then runs `ruff check`, `ruff format --check` and `mypy` over the package. Part of `test:ci:release`. | No |
| `examples/buttons/server/fastapi/bin/ci` | The Buy a Button FastAPI example's CI, the twin of the Rails `bin/ci`. It runs `uv sync --frozen`, the stubbed-wallet tests over `openreceive.testing` (order → invoice → settle → download), the catalog/artwork drift check, the shared-boundary check (no `shared/server-node` imports) and `pip-audit` on the locked environment. The per-push `fastapi-example` job and the weekly `buttons-fastapi` job run this. | No |
| `npm run release:pypi:plan` / `release:pypi:build` | `plan` is a read-only PyPI release plan: root version → PEP 440, and `_version.py` drift. `build` runs `uv build` into `.release/pypi/<version>`, then the wheel-contents check (`unzip -l` for the CLI, the FastAPI binding, the Django migrations and static assets), then `twine check --strict`. `publish-pypi.yml` publishes (trusted publishing, `pypi` environment). `release:pypi:publish` is the token-based fallback. | No |
| `npm run test:php` | Tests the PHP engine (`packages/php/openreceive`) through `tools/ci/php-tests.sh`. It runs `composer validate` per package, `composer install` when `vendor/` is missing, and every PHPUnit suite found by glob. An empty glob is a hard failure. Last, it runs the cross-language harness `tools/conformance/php-crosslang.php`, which sends every shared vector family through the production PHP functions. Needs PHP 8.2+ and Composer on `PATH`. The repository tests run on in-memory sqlite. They also run against real servers when `OPENRECEIVE_TEST_PGSQL_DSN` / `OPENRECEIVE_TEST_MYSQL_DSN` (plus optional `_USER` / `_PASSWORD`) are set. | No |
| `npm run test:e2e:btcpay` | Playwright suite for the BTCPay plugin (`tests/e2e-btcpay`). It runs in Chromium against the running regtest stack. Start the stack with `packages/dotnet/docker/up.sh`, then run `e2e.sh` once to save an API key. It covers the setup page, the doctor, Lightning checkout, the swap component through to "Invoice Paid", the refund form and the pill switch. `packages/dotnet/docker/browser-e2e.sh` runs it inside the official Playwright image on the stack's network. The full suite runs on demand. The setup/save smoke runs on each PR and push. | No |
| `npm run test:e2e:btcpay:smoke` | Build the plugin and start an isolated Docker stack with the pinned BTCPay image and a generated test wallet. Chromium tests preflight, save, reload, and opening a BTC checkout invoice. Runs in the `dotnet-plugin` CI job on every PR and push to master. Requires `npm ci`, Docker Compose >= 2.24.4, and the BTCPay submodule. Uses no host ports and removes its disposable containers/volumes on exit. | No |
| `npm run test:btcpay:latest` | Resolve the latest stable BTCPay release, fetch its source and matching official Docker image, build and run unit tests plus browser save/reload/checkout smoke. When the commits differ, it also tests a plugin built against the pinned source on the latest server. Uses isolated build directories and leaves the submodule pin unchanged. Runs on every pull request, master push and `btcpay-v*` tag. It runs in Release Dry Run on every `v*` tag, weekly, and on demand. The local npm publisher runs it when no green release CI is available. Requires Docker, Git, `npm ci` and network access. Records commits, image digest and outcome in `.release/btcpay-compatibility/latest.json`. | No |
| `npm run test:dotnet` | The BTCPay plugin's xunit suite (`packages/dotnet/BTCPayServer.Plugins.OpenReceive.Tests`). It covers vector conformance for every family the `dotnet` coverage entry does not exclude, plus kernel tests against the in-process testkit wallet and fake provider. It builds the solution and runs the tests in the .NET SDK Docker container through `packages/dotnet/docker/test-unit.sh`. You need no host SDK and no regtest stack. Requires running Docker and the BTCPay submodule (`git submodule update --init --depth 1 packages/dotnet/submodules/btcpayserver`; or set `BTCPAY_SERVER_ROOT`). Missing prerequisites fail explicitly. It reuses the NuGet cache and separate container build directories. `-- --filter <expr>` narrows the run. CI uses the same Docker runner in `dotnet-plugin`. `test:ci:release` includes it. | No |
| `packages/dotnet/docker/up.sh` then `packages/dotnet/docker/e2e.sh` | The BTCPay regtest end-to-end stack, entirely in Docker Compose. `up.sh` builds the plugin in the SDK image and starts bitcoind, NBXplorer, Postgres, two LNDs, a TLS Nostr relay, the testkit NWC service, the fake LSC provider and the latest stable BTCPay. It then funds regtest. `e2e.sh` proves a Lightning payment, a swap, a refund and the spend-capable refusal over HTTP. Run it on demand only, never per push. `down.sh --volumes` wipes it. | No |
| `npm run demo btcpayserver` | On every start, resolve and pull the latest stable BTCPay server. This also happens with `--no-build`, `--published` and `--testkit`, and a lookup or pull failure stops startup. Then start a mainnet BTCPay + Postgres demo at `http://127.0.0.1:14180`, build the plugin, and configure a persistent demo store from root `.env`: `NWC_URI` and optional `LSC_URI_PRIMARY` / `LSC_URI_BACKUP`. It prints the dummy local login. `-- --published` installs the latest compatible stable Plugin Directory package, verifies its checksum, and reuses the same login/store without building source. `-- --stop` keeps the data. `-- --no-build` reuses the local build. `-- --testkit` starts the funded regtest stack instead, without live credentials. | Yes (default and published modes) |
| `npm run test:live:ruby:nwc` | Optional Ruby live-wallet smoke. Reads `NWC_URI` from the environment or root `.env`, redacts the connection string, runs `get_info` when `nwc-ruby` is installed, and creates an invoice only with `OPENRECEIVE_LIVE_CREATE_INVOICE=1`. | Optional |
| `npm run test:live:python:nwc` | Optional Python live-wallet smoke (`tools/live-nwc-test/python-smoke.py`). Reads `NWC_URI` from the environment or root `.env`, redacts the connection string, runs the receive-only preflight over the relay through the in-repo transport, and creates an invoice only with `OPENRECEIVE_LIVE_CREATE_INVOICE=1`. That is the same opt-in as the Node and Ruby smokes. Part of `npm run test:live`. | Optional |
| `npm run test:live:php:nwc` | Optional PHP live-wallet smoke (`tools/live-nwc-test/php-smoke.php`). Reads `NWC_URI` from the environment or root `.env`, redacts the connection string, runs the receive-only preflight through the production `NostrPhpNwcReceiveClient`, and creates an invoice only with `OPENRECEIVE_LIVE_CREATE_INVOICE=1`. That is the same opt-in as the Node, Ruby and Python smokes. It skips clearly when `NWC_URI` is unset or the Composer dependencies are not installed. | Optional |
| `npm run check:generated` | Fail when any generated rendering (TypeScript, Ruby, or C#) or the compiled payment icons are stale. | No |
| `npm run check:demo-containers` | Validate the demo Dockerfiles, compose templates, root `.env` loading, ports, and secret boundaries. This covers the Node demos, the Rails demo, and the `kind: "python"` demos (FastAPI, Django). The Python demos' Dockerfiles must install the engine from `packages/python/openreceive` and must never bake in `.env`. | No |
| `npm run check:release` | Validate release-readiness metadata, package versions, private package status, changelog coverage, that the BTCPay plugin's independent csproj `Version` is valid, and that the Python package's `_version.py` carries the PEP 440 form of the workspace version (stamped by `release:prepare`). | No |
| `npm run check:workflows` | Validate GitHub workflow shape, read-only permissions, safe commands, SHA-pinned actions, and that publishing appears only in `publish-gems.yml` (`gem push`, `rubygems` environment) and `publish-pypi.yml` (`uv publish --trusted-publishing always`, `pypi` environment). | No |
| `npm run build:docs` | Generate all payloads, discovery links and the site contract. Validate manifest coverage. Build `dist/docs` and the complete public-only `dist/openreceive-docs-<version>.tar.gz` import bundle with public search and a SHA-256 source inventory. | No |
| `npm run build:demo` | Build the Buy a Button demos. | No |
| `npm run test:package-smoke` | Pack every JS workspace package into local tarballs, assemble an offline temporary project, and import each package. | No |
| `npm run test:package-assets` | After `build:packages`, extract npm tarballs into an isolated install and test React/custom-element images in Chromium under esbuild (single-file and split), Vite, webpack, and the standalone release archive. Decode every published image, forbid image requests, and verify caption fallback on a failed tutorial chunk. Requires Chromium; runs on the host or in Docker. The per-PR `package-assets` job uses Docker. | No |
| `npm run test -w @openreceive/example-buttons-rails` | The Buy a Button example's catalog/artwork drift check (`script/check-catalog-artwork.mjs`). This is not its test suite. The suite is `bin/rails test`. `bin/ci` runs setup, the stubbed-wallet integration tests, the schema and catalog drift checks, the shared-boundary check and the gem audit, and is what the per-push `rails-example` CI job runs. | No |
| `npm run test:live:nwc` | Live wallet smoke harness. Reads `NWC_URI` from the environment or root `.env`, checks `tools/live-nwc-test/expected_capabilities.json` by default, then skips clearly when unset. It stops after preflight unless `OPENRECEIVE_LIVE_CREATE_INVOICE=1`. That is the same opt-in as the Ruby smoke, so one command means one thing on both engines. | Optional |
